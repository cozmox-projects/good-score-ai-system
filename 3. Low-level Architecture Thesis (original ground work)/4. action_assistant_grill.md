# Action Assistant — User Journeys, Features & Technical Grilling

> Continuation of the grilling docs. This doc covers: (1) the user journeys that justify this role existing at all, (2) the product features they map to, and (3) the hard architecture questions you raised — answered with researched, current numbers, not vibes.

---

## Part A — User Journeys

The brief frames this simply — *"help users complete actions"* — but underneath that is the only role in this system that **changes real money and real legal state.** Six journeys, ordered roughly by how many steps and how much waiting each one involves:

### Journey 1 — "Set a reminder / enable AutoPay." (Single-step, instant)
User wants a bill reminder or AutoPay turned on. No external party involved, no waiting.
**Feature it maps to:** A single synchronous action — call one API, confirm immediately. The simplest possible shape this role takes.

### Journey 2 — "Pay this bill / EMI now." (Single-step, but money moves)
User wants to pay a bill or EMI right now, through the app.
**Feature it maps to:** A payment action — still conceptually one step from the user's view, but the backend now needs payment-gateway confirmation before it can say "done," and this is the first journey where idempotency genuinely matters (a retried request must never double-charge).

### Journey 3 — "Raise a dispute for incorrect bureau data." (Multi-step, external party, slow)
User flags a wrong entry on their report. This isn't resolved in the same request — it has to be filed with a bureau, tracked, and the user needs to see status days or weeks later.
**Feature it maps to:** A long-running, multi-phase process: file → awaiting bureau response → resolved/rejected, with the user able to check status at any point without the request restarting.

### Journey 4 — "I'm going to miss this EMI — help me restructure it." (Multi-step, needs user confirmation mid-flow, external party)
This is the journey you specifically described — the system needs to check affordability, propose a restructuring plan, **show the user a screen to confirm specific new EMI terms**, then submit the negotiated request to the lender, and the user must be locked out of submitting a second, conflicting restructuring request while this one is in flight.
**Feature it maps to:** The hardest journey in this role — multi-step, waits on a human mid-process (not just at the end), waits on an external lender's response, and has a hard one-active-request-per-loan constraint. Covered in depth below.

### Journey 5 — "Apply for a loan." (Multi-step, needs user confirmation mid-flow, external party, regulatory)
User wants a new loan from GoodScore's lending marketplace. Eligibility check → offer selection (a UI moment) → KYC/document upload (another UI moment) → submission → lender decision.
**Feature it maps to:** Structurally similar to Journey 4 — multiple phases, multiple points where the user must see a screen and act, an external party's response in the middle — but with more regulatory checkpoints (KYC, digital signature on terms).

### Journey 6 — "Close this loan / credit card." (Multi-step, often needs a settlement negotiation first)
User wants to close an account — sometimes simple (paid off, no balance), sometimes requires the same restructuring-style negotiation as Journey 4 if there's an outstanding balance to settle first.
**Feature it maps to:** A process that can branch — straightforward closure if no balance, or a fork into something resembling Journey 4's negotiation flow if there's a balance to settle.

**The pattern across all six:** these journeys fall into two genuinely different shapes. Journeys 1-2 are **fire-and-confirm** — fast, single-step, resolved in one request. Journeys 3-6 are **long-running, multi-phase, sometimes-paused-for-a-human-or-an-external-party** — and that distinction is the single most important fact shaping every answer below, because the two shapes need different infrastructure, not the same infrastructure used twice.

## Part B — The Questions, Grilled

### Q1. How does the backend actually talk to the frontend in real time at 5M MAU — bare-metal WebSockets, a managed service, or something else?

This came up as a prerequisite question while working through how Action Assistant tells the frontend "move to this screen now" — and it's a real, standalone infrastructure decision, not a detail to bury inside one journey.

**Bare-metal WebSockets, hand-rolled:** the concern about this breaking at scale is well-founded. Researched industry data shows **65% of DIY WebSocket implementations hit significant downtime**, building one in-house averages **10.2 person-months**, and roughly half end up costing **$100K–200K/year just in upkeep**. At 5M MAU, this is also a genuine distributed-systems problem on its own — you'd need sticky sessions, a pub/sub backplane across servers, OS-level connection tuning, backpressure handling. Building this yourself is its own multi-month project, not a side detail of Action Assistant.

**Managed SaaS (Ably, Pusher, PubNub):** Ably is the strongest of these technically — it's the only one with protocol-level exactly-once delivery, which actually matters here given everything established about idempotency below. But the cost doesn't survive contact with GoodScore's revenue reality: even at Ably's best-case volume-discounted rate, the **MAU base fee alone is ~10% of total monthly revenue** — and that's before connection-minutes, per-message, and bandwidth charges that scale further with actual usage (every workflow status update is a message). At the standard rate it's over **50% of revenue**. This is the same pattern that ruled out paid managed services at scale elsewhere in this system.

**Open-source, self-hosted (Centrifugo):** this is the real answer, and it fits the "production-ready from day one" requirement precisely. It's purpose-built exactly for this gap — open-source, self-hosted, benchmarked at **1 million WebSocket connections and 30 million messages/minute on a single modern server**. It handles the hard distributed-systems parts (connection management, pub/sub backplane, reconnection/message recovery) so there's no need to build that 10.2-person-month project from scratch. And critically: **Centrifugo natively supports both WebSockets and SSE as transports from the same server** — so it's not "pick one transport for the whole system," it's "pick the right transport per use case, served by the same infrastructure."

**Recommendation: self-hosted Centrifugo as the shared real-time messaging layer.** This isn't just an Action Assistant decision — it's infrastructure other roles in this system can ride on too (proactive nudges, live session state), the same way the self-hosted GPU footprint became shared infrastructure across roles elsewhere in this system.

### Q2. Job queue vs. workflow engine — is Redis + BullMQ the right foundation, or does this need something heavier?

You raised this directly, and it's the right place to start, because it determines everything downstream.

**The core distinction, researched directly:** a queue like BullMQ guarantees a worker *receives* a job. It does not guarantee the job *completes correctly* across multiple steps — what happens inside the job, whether it partially finishes, and how to resume after a crash are explicitly outside a queue's contract. The standard way teams compensate is by hand-rolling progress tracking — writing state to Redis or a database, checking it at the start of each step, skipping what already ran. That's exactly the kind of manual bookkeeping your original note flagged as a concern ("multiple steps... manually fed into the LLM backend").

A **durable execution engine** (Temporal is the dominant one, with real production weight behind it — processing trillions of lifetime executions, used at companies running payment- and account-state workflows) closes this gap differently: every step of a workflow is persisted as an event in a history log. If a worker crashes mid-process, the workflow resumes from exactly where it stopped — not from the beginning, and not from a manually-checked status flag.

**Where this matters most for GoodScore specifically:** Journeys 1-2 (single-step, instant) genuinely don't need this — a queue is the right, simpler tool there. Journeys 3-6 are precisely the case durable execution exists for: multi-step, must-survive-a-crash-without-double-submitting-to-a-lender, must-wait-indefinitely-for-a-human-or-an-external-party's-response. Using a plain queue for these means building (and maintaining) your own crash-recovery and progress-tracking logic by hand — the exact manual-bookkeeping problem.

**Recommendation: two different tools for two different shapes, not one tool stretched to cover both.**
- **Journeys 1-2 (fire-and-confirm):** Redis + BullMQ is the right call — simple, fast, low operational overhead, and these jobs are short-lived enough that a crash mid-job just means "retry from scratch," which is fine here.
- **Journeys 3-6 (long-running, multi-phase, human-and-external-party-waiting):** a durable execution engine, not a queue. This is a genuine infrastructure decision with real operational cost (running a Temporal cluster is heavier than running Redis), but the alternative is re-building Temporal's core guarantees by hand inside application code — state machines backed by database tables, custom scheduling for timeouts, manual recovery scripts — which is more total engineering effort, not less, and is exactly the trap the research describes teams falling into.

### Q3. Idempotency — what actually needs to be idempotent, and is an idempotency key enough on its own?

You flagged this as "very important" — worth being precise about, because there are actually two different guarantees being asked for here, and conflating them is a common mistake.

**Guarantee 1 — request-level idempotency.** The same network retry of the same request must not execute twice. This is the standard pattern: client generates a UUID per request, server checks if that UUID has already been processed, and if so returns the original result instead of re-running the operation. This protects against network glitches and double-taps on a button.

**Guarantee 2 — business-entity locking.** This is what your phrasing was actually reaching for: *"until and unless we lock the user to raise the request for EMI restructuring."* That's not about retries — it's about preventing **two genuinely different restructuring requests** for the same loan from both being in flight at once, even if both are individually well-formed, idempotent requests with different keys. An idempotency key alone doesn't catch this, because two distinct user actions ("restructure into 5 EMIs" then, before that resolves, "actually, restructure into 3 EMIs") would carry two different, individually-valid keys.

**Recommendation: both layers, not one standing in for the other.**
- **Request-level:** standard idempotency key (UUID, generated client-side, checked server-side before any action is taken) on every Action Assistant request that touches money or external state.
- **Business-entity level:** a lock tied to the actual entity being acted on (e.g., `loan_id` for Journey 4, `account_id` for Journey 6) — once a restructuring workflow is active for a given loan, any new restructuring request for that *same loan* is rejected outright (or surfaced as "you already have one in progress, here's its status") regardless of idempotency key. In a durable-execution model this maps naturally: the workflow's own ID can be derived from the loan ID itself, so starting a second workflow for a loan that already has one running simply returns the existing, in-progress execution instead of creating a conflicting one.

### Q4. How does a multi-step workflow show the user a screen mid-process, and how does the user actually find their way back to a paused request — possibly days later?

This was the part of the original framing that doesn't have an obvious answer from job-queue thinking alone — the note flagged it explicitly: *"there would also be scenarios where we'd need to showcase certain UI screens to the user in certain step of an action."* Pressure-testing that surfaced two further questions worth separating: how the backend pauses and resumes internally, and — the part missed initially — how the *user* finds their way back to that paused state at all, especially across sessions and days.

**Part 1 — the backend pause/resume mechanism: signals.** A durable workflow can pause — genuinely pause, consuming zero compute while waiting — at the exact point it needs human input, for an unbounded amount of time (the same mechanism works whether the wait is five seconds or five months). The workflow sets its own state (e.g., `AWAITING_RESTRUCTURING_CONFIRMATION`) and the frontend reads that state to decide which screen to show. When the user acts on that screen — confirms the proposed EMI terms — the action is delivered back into the still-paused workflow as a **signal**, and execution resumes exactly where it left off, with the user's input now available to the next step.

This solves the "map" of steps with UI checkpoints baked in: the workflow definition itself *is* that map. Each phase of Journey 4 becomes an explicit step:

```
1. check_affordability       (automated)
2. propose_restructuring     (automated)
3. AWAIT_USER_CONFIRMATION   <- pauses, frontend shows confirmation screen
4. submit_to_lender          (automated, runs only after signal received)
5. AWAIT_LENDER_RESPONSE     <- pauses, indefinitely, no polling needed
6. notify_user_of_outcome    (automated)
```

**Part 2 — how the user finds a paused request again.** The instinct here was a chat-thread concept — these long-running processes living inside a chat history. Worth separating two different versions of that idea, because they have different implications: (A) the chat history is the literal source of truth the user has to scroll back into, versus (B) chat is one *view* into the request, but the request itself is a first-class backend entity independent of any conversation.

**(B) is the right model.** Think about who actually returns to a paused request: a user starts a restructuring conversation Tuesday, gets a push notification Thursday that the lender responded, and opens the app. They shouldn't have to hunt through chat history to find a two-day-old conversation — they should land directly on a screen showing "your EMI restructuring — awaiting your confirmation." For GoodScore's users specifically — already anxious about money, already in a system they don't fully trust — that's a meaningfully lower-friction path. The chat conversation is *how the request got created*; the request's status afterward shouldn't require remembering or finding the right thread. This also resolves a related concern about whether chat history needs to be a comfortable, parseable interface for every user — it doesn't have to be, if the important thing (an active request's status) is always independently accessible rather than buried in a scrollback.

**Recommendation:** the long-running request is a backend entity, addressable by its own ID (tied to the loan/account it acts on), independent of any chat thread. Chat history can store the conversational exchange, but it is not the resume mechanism — the workflow's own state is.

**Part 3 — how does the backend actually deliver "move to this screen now" to the frontend, and how should that interact with a user who's mid-task elsewhere?** Two different moments call for different handling here.

The first moment — *live, in-session update* — is what Q1's messaging layer (self-hosted Centrifugo) exists for: if the user is actively on the "awaiting lender response" screen and the lender responds while they're looking at it, that update needs to arrive over a live channel, not a delayed notification.

The second moment is closed-app or app-reopen: a normal fetch-on-load API call (`give me the current status of any active requests`) answers this — no persistent connection needed, since the workflow's current phase is the single source of truth the frontend renders against.

**One important revision to the original framing:** the first instinct was that the backend should be able to push the user straight into a paused workflow's screen the moment it needs attention. **That's wrong if the user is in the middle of something else.** A user actively completing a different task in the app — paying a bill, reviewing their report — shouldn't be yanked into an unrelated restructuring confirmation screen mid-task. Instead, when a workflow reaches a phase that needs the user's attention, **it should hand off to the Proactive Assistant** rather than forcing the screen directly. Proactive already owns exactly this judgment call — surfacing the right thing at the right moment, never interrupting an active session, only ever at a closed-app push or the next app-open. Action Assistant produces the *event* ("restructuring proposal ready for confirmation"); Proactive decides *when and how* it actually reaches the user. This keeps the same discipline used elsewhere in this system: each role owns one job, and "deciding when to interrupt a user" is Proactive's job, not something Action Assistant should duplicate.

**Recommendation, consolidated:** workflow phase transitions that need user attention emit an event rather than directly pushing a screen; Proactive consumes that event and decides delivery (live update if in-session and on a relevant screen already, otherwise a push notification or next-app-open surfacing); the workflow's own state remains the single source of truth for which screen renders, whenever the user does arrive.

### Q5. Should each action be one API call that does everything internally, or does the multi-step structure need to be visible at the API/tool layer too?

This was raised as an open fork: *"whether we should create APIs/tools for each actionable where steps would be executed inside the API call... that would also not be synchronous in nature instead same job would go through multiple phases."*

**Recommendation: the LLM-facing tool layer should be thin and phase-agnostic; the workflow engine owns the actual multi-step structure underneath.** Concretely: the LLM calls something like `start_emi_restructuring(loan_id)` — one tool, one call. That call's job is just to start (or return the existing) durable workflow for that loan and hand back a status/reference. The LLM doesn't need to know or orchestrate the 6 internal phases from Q4 — it asks "what's the status of this user's restructuring request," and the workflow's current phase answers that question directly. This keeps the LLM's job consistent with the design established for this system generally — deciding *which* tool to call and narrating the result, not owning multi-step business logic itself. The complexity of "this is actually 6 phases with 2 human waits and 1 external-party wait" lives entirely in the workflow definition, invisible to the LLM layer.

### Q6. What's the actual cost and operational footprint of this role at GoodScore's scale?

Worth being honest about, since this is the first role in this system that introduces genuinely new infrastructure — both the messaging layer (Q1) and a durable execution engine — rather than purely reusing what other roles already justified.

**The honest case:** running a production durable-execution cluster (self-hosted Temporal, for instance) is real, ongoing infrastructure — not a per-token or per-call cost like an LLM API, but a fixed operational cost (compute for the cluster, the database backing it, the team's time to operate it) that exists regardless of volume, similar in shape to the self-hosted GPU footprint and the self-hosted Centrifugo layer already justified elsewhere in this system. The actual per-workflow cost is small — these workflows are mostly waiting, not computing, and a paused workflow consumes no compute while idle — so the cost scales with the *number of distinct workflow types and the engineering/ops investment*, not linearly with MAU the way a per-conversation cost would.

**Recommendation:** treat both the durable execution engine and the Centrifugo messaging layer as **fixed infrastructure, justified once** — the same way the self-hosted voice stack was justified for the system's highest-volume role, these are justified by being the only sound way to handle money-moving, multi-party, must-not-corrupt-state workflows correctly, not by a per-user cost comparison against a managed alternative. The genuine cost discipline question isn't "should we afford this" — it's "how many of the six journeys actually need the heavy engine vs. how many can stay on the cheaper queue," which Q2 already answers (2 of 6 stay cheap; 4 of 6 need it).

## Summary

**The honest takeaway:** Action Assistant is the first role in this system where the interesting engineering problem isn't the LLM at all — it's **building a workflow that can survive crashes, wait indefinitely for humans and external parties, show the right screen at the right phase, and never let two conflicting financial actions run against the same account at once.** The LLM's job here is almost incidental — start the right workflow, report its status back in plain language. The real design surface is the workflow and messaging infrastructure underneath it, and three findings carry this doc: (1) bare-metal WebSockets and managed real-time SaaS both fail at GoodScore's scale — one on reliability, the other on cost — leaving self-hosted Centrifugo as the right foundation; (2) a job queue alone is the wrong tool for 4 of the 6 journeys, not a simpler version of the right tool; and (3) "idempotent" and "locked" are two different guarantees that both need to exist, not one substituting for the other — and the paused request itself must be a backend entity independent of any chat thread, with Proactive (not Action Assistant) owning the judgment of when to actually surface it to the user.
