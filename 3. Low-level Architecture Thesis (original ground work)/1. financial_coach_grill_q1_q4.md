> Role 1 of 4 (Coach). This doc covers: (1) the user journeys that justify this role existing at all, (2) the product features they map to, and (3) the hard architecture questions you raised — answered with researched, current numbers, not vibes.

---

## Part A — User Journeys (the "why" before the "how")

Before picking Sarvam vs open-source vs video-vs-voice, we need to be honest about _what moment in the user's life_ the Coach is showing up in. Six journeys, ranked by frequency × emotional stakes:

### Journey 1 — "Why is my score what it is?" (First report view)

A user opens the app post-recovery, sees a number (642), and has zero context for what it means or why it's that number specifically.
**Feature it maps to:** Personalized score breakdown — factor-by-factor explanation (utilization, payment history, account age, credit mix, inquiries) using _their actual data_, not generic definitions.

### Journey 2 — "Why did my score just drop/rise?" (Score change event)

New bureau pull comes in, score moves ±X points. User is anxious or curious and wants the _causal_ explanation immediately, not three days later.
**Feature it maps to:** Delta explainer — diffs the last two reports, identifies the specific tradeline/event that moved the needle, explains in one or two sentences.

### Journey 3 — "What is this unknown name on my report?" (NBFC confusion)

User sees "Axio" or "Arthimpact" and panics — thinks it's fraud.
**Feature it maps to:** Real-time NBFC-to-brand resolution, conversational, instant (this is actually closer to Product Guide territory, but the _explanation_ of "why does this show up under a different name" is a Coach job — trust-building, not navigation).

### Journey 4 — "Why is my utilization a problem?" (Risk factor deep-dive)

User has been told "reduce utilization" but doesn't understand the mechanism — why does using my own credit limit hurt me?
**Feature it maps to:** Concept explainer that's hyper-personalized — uses their actual card, their actual % utilized, shows what score impact a specific paydown amount would have.

### Journey 5 — "Have I actually been improving?" (Progress / motivation checkpoint)

After weeks/months of effort, the user wants validation that the hard work (avoiding new debt, paying on time) is working. This is a _retention and trust_ moment, not just informational.
**Feature it maps to:** Periodic progress narrative — monthly/quarterly recap video or message: "3 months ago you were at 642. Today you're at 670. Here's specifically what you did right."

### Journey 6 — "I don't understand bureau jargon at all" (Low financial literacy onboarding)

First-time credit users or people who've never had anyone explain what a "hard inquiry" or "DPD" (days past due) means.
**Feature it maps to:** A vernacular glossary layer baked into every explanation — the Coach never says "DPD" without immediately explaining it the first time, then can use shorthand once it's confirmed the user understood.

**The pattern across all six:** every single journey is triggered by _something changing in the user's actual data_ — a new report, a missed payment, a paydown, time passing. This tells us something architecturally important before we even get to voice vs video: **the Coach is fundamentally event-driven and data-grounded, not a general chitchat agent.** That constrains every answer below.

## Part B — The Questions, Grilled

### Q1. Voice agent (Sarvam/Indic LLM) vs open-source Indic stack — cost and performance

I looked this up rather than guess, because the numbers genuinely matter here.

**Sarvam AI pricing (as of mid-2026):**
| Component | Price |
|---|---|
| STT (Saarika/Saaras) | ₹30/hour of audio (~$0.000092/sec) |
| TTS (Bulbul v2/v3) | ₹15–30 per 10,000 characters |
| Chat/LLM (Sarvam-30B/105B) | Token-based, separate pricing |

Sarvam's real edge isn't raw price — it's handling code-mixed speech like Hinglish and Tanglish naturally, with around 250ms latency suitable for live conversation, and it tends to come out 20-30% cheaper than stitching together Whisper plus GPT-4o for Indian language tasks, with better regional accuracy.

**Open-source alternative (AI4Bharat IndicConformer + Indic Parler-TTS):**

- IndicConformer-600M is described as India's first open-source ASR system covering all 22 official languages at this scale, MIT licensed, free on HuggingFace. One implementation runs on CPU only — 2 vCPUs and 4GB RAM on Cloud Run, with optional GPU/CUDA mode for faster inference.
- For TTS, an open-source wrapper around ai4bharat/indic-parler-tts supports 22 languages with 69 pre-built voices and emotion/tone control, fully self-hosted with zero API cost.
- Infra cost for self-hosting at moderate volume: roughly ₹50,000–1,00,000/month for a production-grade GPU instance, flat regardless of call volume (within capacity).

**My recommendation:** Don't pick one exclusively — **use Sarvam for launch, build toward open-source as volume scales.** Here's the actual decision logic:

- At low-to-moderate volume (pilot, first 6–12 months), Sarvam's pay-per-use model means you pay for what you use, you get production-grade accuracy on code-mixed speech (which your users _will_ do — Hinglish is the default register for this demographic), and you avoid owning GPU infra, model drift, and fine-tuning overhead.
- The crossover point is volume-driven, not time-driven. Do the math: Sarvam STT+TTS for a typical 2-minute coaching conversation (≈300 words spoken by user, ≈400 words spoken back) costs roughly ₹2–4 per session in API fees. At 1 million monthly active _voice_ sessions, that's ₹20–40 lakh/month. Self-hosted IndicConformer + Indic-Parler-TTS at ₹50K–1L/month flat is dramatically cheaper _once you're past roughly 15,000–25,000 sessions/month_ on a single GPU instance (scaling horizontally beyond that).
- So: ship on Sarvam, instrument your actual session volume and language-mix data from day one, and set an explicit trigger ("when monthly voice sessions exceed X, kick off the self-hosting migration") rather than a vague someday plan.

One nuance worth flagging back to you: open-source Indic ASR/TTS quality on **noisy, accented, code-mixed speech from your specific demographic** (Tier 2/3 city, financially stressed, possibly older or less app-literate users) is not guaranteed to match Sarvam's out of the box — Sarvam has done dedicated work on this exact use case. You'd want to benchmark both against a sample of your real user calls before committing to self-hosting, not just trust the benchmark claims.

## Q2. Video strategy — manual library vs. self-hosted AI avatar vs. general-purpose text-to-video model

You asked three real options. I priced all three.

### Option A — Manually-mapped video library (human or AI-recorded once, reused for all matching users)

This is "record ~80-90% of common scenarios once, map users into the closest matching template."

**Cost structure:** one-time production cost (CapEx), near-zero marginal cost per view thereafter (just CDN bandwidth).

```
Estimate: 50-150 template videos x Rs.15,000-40,000/video
(human presenter, professional shoot/voiceover, multi-language dubbing into 5 languages)

One-time cost range: Rs.7.5 lakh - Rs.60 lakh (total, not recurring)
Marginal cost per view thereafter: ~Rs.0
```

**What this actually means:** spend roughly ₹10-30L once, building a library that covers the score-band × factor-combination × language matrix (e.g., "score 600-650, utilization-driven, Hindi" is one template), and every user who matches that bucket sees the same video. It's not _fully_ personalized — it's personalized at the segment level, not the individual level.

**This is the model GoodScore's founder actually described in the VC interview** — "we create YouTube-like videos that people can consume at will," hyperpersonalized in the sense of _referencing the user's actual account names and numbers as overlaid text/data_, not necessarily a fully bespoke video render per person. Worth noting: the founder's description sounds more like **dynamic data overlay on a templated narration structure** than a from-scratch AI render per user. That's actually a fourth option worth considering — more on this below.

### Option B — Self-hosted AI avatar (script → TTS → Wav2Lip lip-sync), truly personalized per user

This is the architecture Gemini's research described: LLM writes a personalized script from the user's real data → TTS converts it to audio (reuse the open-source Indic-Parler-TTS stack from Q1) → Wav2Lip lip-syncs a base avatar video to that audio.

**GPU cost (L40S-class, researched):**

```
L40S hourly rate: $0.50-2.25/hr (spot to on-demand) = ~Rs.44-198/hour
Wav2Lip inference: roughly real-time to 2-3x real-time per video on a single GPU
=> a 60-second personalized video costs ~Rs.4.84 in GPU compute (using blended mid-rate,
   assuming ~25 such videos processed per GPU-hour)
```

That per-video cost looks cheap in isolation. The problem shows up when you multiply by MAU:

```
If avg user gets 0.5 video-worthy events/month (conservative):
  2,500,000 videos/month -> Rs.1.21 Cr/month -> 27.9% of ACTUAL monthly revenue

If avg user gets 1 video-worthy event/month (e.g., monthly score check-in):
  5,000,000 videos/month -> Rs.2.42 Cr/month -> 55.7% of ACTUAL monthly revenue

If avg user gets 2 video-worthy events/month:
  10,000,000 videos/month -> Rs.4.84 Cr/month -> 111.5% of ACTUAL monthly revenue
  (exceeds total company revenue)
```

**This is the real finding:** even the _cheap, self-hosted_ personalized video option breaks the business at realistic frequency. At just **one personalized video per user per month**, you're spending over half the company's entire monthly revenue on video generation alone — before LLM costs, voice costs, hosting, or anything else.

### My recommendation — and the reframe I think actually matters

Between A and B, here's the honest tension: **B is "more personalized" but financially breaks the business at any real frequency. A is "less personalized" but is the only one that's actually affordable at this MAU.**

But I don't think it has to be a strict either/or. Here's the hybrid that I think matches both the founder's own description _and_ the unit economics:

**Default to Option A (templated library) as the backbone, with Option B (true AI-personalized video) reserved as a scarce, high-leverage asset — not a per-event default.**

Concretely:

- Build the ~80-100 template library covering score bands × dominant risk factor × language. This handles Journeys 1, 3, 4, 6 from our journey list (first report explanation, NBFC confusion, utilization explainer, jargon glossary) — these are fundamentally _the same explanation_ reused across millions of similar users, just with their specific numbers overlaid as on-screen text/data (cheap — this is just templated string interpolation into video captions/lower-thirds, not video regeneration).
- Reserve true Wav2Lip personalized video generation for **Journey 5 (progress recap)** specifically — the genuinely high-trust, high-retention moment ("3 months ago you were at 642, today you're at 670, here's what you did right") — because that's the moment where bespoke personalization has the highest emotional ROI per video generated, and it can be capped to a deliberate cadence (e.g., quarterly, not monthly) rather than firing on every score check.
- That alone would cut Option B's frequency from "1-2x/user/month" down to "1x/user/quarter," which divides the cost by 3-6x — bringing it back into a defensible single-digit percentage of revenue.

## Q3: Voice Orchestration (LiveKit vs Pipecat)

### The basic difference, in plain words

**LiveKit is built like a conference call system** — its core strength is handling many people in one call at once (think Zoom). It can also run a voice AI agent inside that call.

**Pipecat is built like a phone call with a robot** — designed from day one for exactly one person talking to one AI, smoothly.

GoodScore's Coach is always 1 user + 1 AI. Nobody else joins that call. So on paper, Pipecat looks like the better shape-match — LiveKit's "many people in a room" strength is something we'd never use.

---

### But shape-match isn't the only thing that matters — here's what changed the answer

#### 1. Integration with Sarvam / open-source models — no real difference

Both LiveKit and Pipecat have official, ready-made connectors for Sarvam (just install and go). Both also let us plug in our own self-hosted models (the AI4Bharat-style open-source stack we picked in Q1) without being locked out. Neither one wins here — this wasn't the deciding factor.

#### 2. Development speed and maintenance — this is where it actually matters

This is the part that changed my answer. The real question isn't "which one is more elegant for our use case" — it's **"which one means less code that we have to build and maintain ourselves, forever."**

**LiveKit comes with a lot of the hard stuff already built and maintained by their team:**

- Handling when a user interrupts the AI mid-sentence
- Detecting when someone has stopped talking
- Managing the live connection at scale
- A ready-made pattern for **handing off a conversation from the AI to a real human agent** mid-call, while keeping the conversation history intact — directly useful for GoodScore's "AI escalates tricky cases to a human" idea

**Pipecat gives you clean building blocks, but more of the production-grade plumbing is on us:**

- Deploying and scaling it in production
- Building the human-handoff behavior ourselves if we ever need it
- More of "you assemble the final building yourself"

One industry comparison put the tradeoff exactly like this: _Pipecat gives you control but demands infrastructure work. LiveKit ships faster but limits your architectural choices._

That's the real cost. Manual code isn't just slower to write once — it's something our team has to keep fixing and updating for as long as the product exists. A pre-built, actively maintained solution means that burden sits with LiveKit's team, not ours.

---

### The business lens — what actually decided this

You were clear about the priority: **machinery we don't use isn't the concern. Shipping a production-ready solution fast, at 5 million MAU, is the concern.**

Once the question is framed that way, the "unused machinery" objection to LiveKit stops mattering — paying a small architectural overhead for capability we don't need is a non-issue if it means we ship faster and maintain less code ourselves. What matters is: which option gets a reliable, production-grade voice experience in front of 5M users sooner, with less ongoing engineering burden on a small team.

On that question, LiveKit wins clearly:

- Production transport, scaling, and interruption-handling are already solved and maintained by LiveKit, not us.
- The human-handoff pattern (AI → real agent) is already built — relevant given GoodScore's own founder talks about reserving humans for complex escalations.
- Less custom code for our team to own means fewer things that can break as we scale to 5M MAU, and fewer engineering-hours spent on infrastructure instead of the actual product.

---

### Final answer for Q3

**Go with LiveKit**, self-hosted (to keep costs aligned with our Q1 decision), connected to our chosen voice stack (Sarvam to start, migrating toward the self-hosted open-source Indic stack as discussed in Q1).

This reverses our earlier lean toward Pipecat. The shape-match reasoning (1:1 conversation, no need for multi-party rooms) was correct on paper, but it wasn't the right axis to decide on — once "ship fast and maintain less code at 5M MAU" is the actual business priority, LiveKit's pre-built, maintained infrastructure outweighs the fact that some of its capability (multi-party rooms) goes unused. We're not paying for unused machinery in any way that matters to the business — we're paying for not having to build and maintain that machinery ourselves.

## Q4: LLM Backend, Agent Framework & Data Layer

> Continuation of the Financial Coach grilling doc. This is the "brain" layer — what powers the actual reasoning behind every journey we mapped in the original doc (score breakdowns, delta explanations, NBFC resolution, utilization deep-dives, progress recaps, jargon explanations). Same constraints carried forward from Q1–Q3: **5M MAU, ₹100/month paywall, real revenue ~₹4.34 Cr/month**, self-hosted-by-default posture wherever the economics support it.

---

### The starting question

Gemini's original research proposed a fairly standard architecture for this layer: a Text-to-SQL pipeline (LLM writes SQL queries against the user's financial data, with schema-linking and a self-correction loop), a tiered model-routing system (cheap model for navigation, mid-tier for explanation, frontier model for complex reasoning), and a vector-database-backed RAG layer for retrieval.

We pressure-tested this against the actual user journeys and against real production experience, and landed somewhere meaningfully different on the most important piece.

---

### Part A — How the Coach actually gets its facts: deterministic tools, not Text-to-SQL

This was the most important call in this whole layer, and it came from pushing back hard on Gemini's default recommendation.

**The problem with Text-to-SQL here:** Gemini's research proposed letting the LLM write SQL queries on the fly against the user's credit data — with schema-linking, a planning step, and a self-correction loop if the query fails. That's a reasonable general-purpose pattern. But it's the wrong tool for this specific job, for a reason that matters more here than almost anywhere else this could be used: **even a very high-accuracy Text-to-SQL system is still stochastic.** The LLM is generating a _new_ query for every request — it can join the wrong table, miss a filter, or silently misinterpret what "Total Dues" means in a particular schema. General-purpose Text-to-SQL research itself acknowledges this is an open, unsolved reliability problem, especially as schemas grow — retrieval can become a bottleneck and errors compound.

In most products, an occasional wrong SQL join is an annoying bug. In this product, it's **a financial app telling a stressed, low-literacy, in-recovery user an incorrect number about their own debt.** That's not a quality issue, that's a trust-destroying event for exactly the demographic GoodScore exists to serve — people who've already been burned by confusing, opaque financial systems once.

**The fix: deterministic tools, not generated queries.** Instead of letting the LLM write SQL, we pre-build a library of tested, fixed backend API endpoints — each one a known, validated query — and expose these to the LLM as **tools it can call**, the same way a coding agent calls a "run tests" or "search files" tool rather than writing raw shell commands from scratch every time. The LLM's job shrinks to: understand what the user is asking, pick the right tool (or sequence of tools), pass it the right parameters, and narrate the result back in plain language. The actual number that reaches the user never passes through a generative, error-prone step — it comes straight from a query someone wrote and tested once.

This also turns out to map naturally onto the original six journeys, because **every single one of them is a known, finite shape of question dressed up as open conversation** — "what's my score breakdown," "what changed since last time," "what is this NBFC," "what does this utilization cost me," "how have I progressed," "explain this term." None of these need arbitrary, unbounded querying. They need a fixed, well-tested toolset that covers a known problem space.

---

### Part B — Tool design: a catalog, not a fixed count

The first instinct was to map tools roughly 1:1 to journeys — maybe four or five clean, single-purpose tools. That instinct was wrong, and the reason why matters architecturally.

**The "what" journeys are simple. The "why" journeys aren't.** Journey 1 ("why is my score what it is") is a single lookup — fetch the score breakdown, done. But Journey 2 ("why did my score just drop or rise") is fundamentally a **diagnostic investigation**, not a lookup. A score change could be caused by a missed payment, a utilization spike on a specific card, a new hard inquiry, an account aging past a threshold, or a closed account changing the user's credit mix — and the AI doesn't know which one applies until it starts checking. That means the LLM may need to call several tools in sequence — check the delta, then branch into checking payment history, then utilization, then inquiries — based on what each step actually reveals, not according to a fixed script.

So the right design isn't "N tools, one per journey." It's a **tool catalog**: a library of narrow, single-purpose, well-documented data-fetching functions (score breakdown, payment history lookup, utilization-by-account, inquiry history, NBFC name resolution, account-age lookup, and so on), each with clear metadata telling the LLM _when_ it's the right tool to reach for. The LLM composes these at runtime, chaining as many as the investigation actually requires. A simple "what's my score" question might call one tool. A "why did it change" question might call four, inspecting each result before deciding whether it needs another.

This is also why the orchestration layer underneath this needs to support genuine looping behavior — call a tool, look at what came back, decide whether that's enough or whether another tool is needed — rather than a fixed, one-shot "call tools then answer" pipeline. More on that in Part D.

---

### Part C — LLM choice: paid frontier model first, self-hosting only once volume justifies it

Given Part A and B narrowed the LLM's actual job down to **intent understanding, tool selection, tool-chaining, and narration** — not raw financial reasoning from scratch — this is a smaller, more contained job than "be a financial expert." That actually makes the choice here more clear-cut than it was for voice in Q1.

**The numbers, researched directly rather than assumed:**

Self-hosting an open-source model only beats a paid API once you cross a real, measurable volume threshold — roughly **5 million tokens/day of sustained traffic** for a single mid-size open-weight model (this is the threshold reported across multiple 2026 cost-breakdown analyses comparing GPU rental costs against current API pricing). Below that line, a paid API is cheaper once you account for the GPU rental, the ops overhead of running inference infrastructure, and the engineering time spent keeping a self-hosted model healthy — all things that don't show up in a simple per-token price comparison but are very real costs.

We don't yet have GoodScore's actual Coach-query token volume — we estimated _session counts_ in Q1 (1.65M–9.9M sessions/month depending on engagement assumptions), but token volume per session for the reasoning/tool-calling layer specifically is a different, currently-unknown number.

There's also a reliability dimension that matters more here than it did for voice: **tool-calling correctness.** An open-source model picking the wrong tool, or malforming a function call, is a structurally different and arguably worse failure mode than slightly less natural-sounding prose — it's the difference between "explains it a bit clumsily" and "fetches the wrong piece of financial data entirely." Frontier paid models are currently more dependable specifically at structured tool-selection, which is the exact skill this layer leans on most heavily.

**The call: start with a paid frontier model (Claude- or GPT-class) for the reasoning/tool-calling layer, not self-hosted, and treat the migration to open-source as something triggered by real measured volume data crossing the known breakeven — not a someday plan.** This mirrors the discipline we applied to the voice stack in Q1, except here the threshold is a concrete, externally-validated number (5M tokens/day) rather than something we have to estimate from scratch. Once production telemetry tells us where we actually sit relative to that line, the migration decision becomes a measurement, not a guess.

---

### Part D — Agent framework: LangGraph, not LangChain alone

Part B's conclusion — the LLM needs to call a tool, inspect what comes back, and decide whether it needs to call another one, looping as many times as a "why did my score change" investigation actually requires — rules out a simple one-shot pipeline. This is **stateful, branching, multi-step agent behavior**, and the framework choice follows directly from that.

LangChain and LangGraph aren't really competing options anymore as of their 2026 v1.0 release — they're explicitly positioned as two layers of the same stack: _LangChain is the agent framework — abstractions and integrations for models, tools, and agent loops. LangGraph is the orchestration runtime — durable execution, streaming, human-in-the-loop, and persistence._ In practice, LangChain provides the scaffolding for defining our tool catalog and wiring up the model, while LangGraph provides the stateful graph execution underneath — the part that actually lets the agent call a tool, branch based on the result, and loop back for another tool call when the investigation isn't done yet.

**The call: LangGraph as the orchestration runtime, built on top of LangChain's tool/integration scaffolding.** This isn't an either/or — it's using each layer for what it's actually built for. The alternative (LangChain's simpler one-shot agent executor alone) would force the "why did my score change" diagnostic chain into a single fixed call sequence instead of letting the LLM genuinely investigate and branch, which defeats the purpose of having a tool catalog in the first place.

---

### Part E — Guardrails: kept intentionally simple

The instinct to build a response-by-response numeric verification layer — cross-checking every number the LLM is about to say out loud against the raw tool output before it reaches the user — was considered and explicitly **not** pursued at this stage. It's the kind of safety net that sounds appealing in the abstract but adds real engineering and latency overhead for a failure mode that Part A's design already substantially reduces (the numbers come from tested tools, not generated queries, so the main remaining risk is the LLM mis-narrating a correct number rather than fetching a wrong one).

**The call: a single top-level guardrail layer**, not granular per-response verification. This keeps the system simpler to build and reason about, and matches the level of risk actually remaining once Part A's deterministic-tools decision is already doing most of the trust-protection work.

---

### Part F — The general knowledge layer (unchanged from earlier discussion)

For the genuinely unstructured, low-stakes layer — explaining what "DPD" or "hard inquiry" means, the kind of fixed-glossary content behind Journey 6 — a **lightweight vector store covering roughly 50–100 fixed concepts** remains the right call. This is a fundamentally different risk profile than a user's actual financial numbers: getting a definition slightly imprecisely worded is not the same category of failure as misreporting someone's outstanding balance, so a vector-similarity lookup is perfectly appropriate here in a way it isn't for Part A's data layer. No knowledge graph — that's a heavier, relationship-modeling tool suited to sprawling interconnected entities, and overkill for what's really a fixed glossary plus a handful of structured financial reports.

---

### Where this leaves the Coach's "brain" layer

| Layer                        | Decision                                                                                    | Why                                                                                                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User's real financial data   | Deterministic tool/API calls (fixed, tested backend queries)                                | Text-to-SQL is stochastic by nature; this is a financial-trust product where a wrong number is a churn event, not a minor bug                                          |
| Tool design                  | A catalog of narrow, single-purpose, documented tools — not a fixed 1:1 mapping to journeys | "Why" journeys (e.g. Journey 2) need multi-step diagnostic chaining; "what" journeys need a single lookup                                                              |
| LLM choice                   | Paid frontier model (Claude/GPT-class) for reasoning + tool-calling                         | Self-hosting only wins past ~5M tokens/day sustained — we don't have that volume data yet; frontier models are more dependable specifically at structured tool-calling |
| Agent framework              | LangGraph (orchestration) on top of LangChain (tool/integration scaffolding)                | The "why" journeys require stateful, branching, multi-step tool-calling loops, not a one-shot pipeline                                                                 |
| Guardrails                   | Single top-level layer                                                                      | Granular per-response numeric verification is excess engineering given Part A already removes most of the risk                                                         |
| General knowledge / glossary | Lightweight vector store, ~50–100 fixed concepts                                            | Low-stakes, genuinely unstructured content — the one place a vector lookup is the right tool                                                                           |

This is a meaningful departure from Gemini's original proposal in one specific, important way: **the data-access layer is deterministic by design, not generative.** Everything else (tiered reasoning, agent orchestration, a lightweight retrieval layer for soft content) ends up in roughly the same place Gemini's research pointed to — but the core trust-critical path now never asks an LLM to invent how to fetch a real financial number.
