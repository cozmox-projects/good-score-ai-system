# Product Guide — User Journeys, Features & Technical Grilling

> Continuation of the grilling docs. This doc covers: (1) the user journeys that justify this role existing at all, (2) the product features they map to, and (3) the hard architecture questions you raised — answered with researched, current numbers, not vibes.

---

## Part A — User Journeys

The brief frames Guide simply: *"help users navigate the application."* That undersells it. Five journeys, each a distinct shape of friction:

### Journey 1 — "Where do I find X?" (Direct navigation request)
A returning user knows what they want but not where it lives in the app — "where do I set up autopay," "where are my disputes."
**Feature it maps to:** Natural language → deep link. User states intent in plain words, app jumps straight to the right screen, no menu-hunting.

### Journey 2 — "I'm stuck mid-task." (In-flow assistance)
User is halfway through raising a dispute or applying for a loan and hits a field or step they don't understand.
**Feature it maps to:** Context-aware help — Guide knows *which screen the user is currently on* and can answer "what does this field mean" without the user having to describe their location.

### Journey 3 — "I want to do something, but I don't know it's possible." (Capability discovery)
User doesn't know GoodScore can set bill reminders, or enable AutoPay, or that disputes can be tracked in-app — so they never ask.
**Feature it maps to:** Light, occasional surfacing of underused features tied to the user's actual behavior (e.g., a user who manually pays the same bill 3 months running gets a one-time "want me to automate this?" nudge) — has to be rare and earned, not pop-up spam.

### Journey 4 — "Something broke / I can't find support." (Friction recovery)
User hits an error, a confusing screen, or just can't find what they need and is one bad experience from uninstalling.
**Feature it maps to:** Fallback escalation — if Guide can't resolve a navigation request after one clarifying attempt, it hands off to either a search/FAQ result or human support, rather than looping the user in confused chat.

### Journey 5 — "I just installed this, where do I even start?" (First-time onboarding)
A brand-new user, possibly never used a credit app before, has no mental model of what's even in here.
**Feature it maps to:** A scripted welcome + guided tour offer, executed the moment the user accepts it.

**The pattern across all five:** Guide is **intent-event-triggered** — it fires when the user expresses a goal ("take me to," "where is," "what does this mean"), not when their underlying financial data changes. This is a fundamentally simple trigger surface, and it shapes every answer below: **Guide doesn't need to reason about financial data at all. It needs to map intent → location, fast and cheap.**

## Part B — The Questions, Grilled

### Q1. Does Guide need an LLM at all — and if so, how big?

This is the first question worth asking honestly, because the brief's examples ("help users navigate the application") sound almost too simple to need AI.

**Research finding:** the literature is unambiguous that navigation/intent-classification is the textbook case for small, cheap models — not frontier ones. Production cost breakdowns describe a now-standard pattern: self-host a small, fast model for high-volume, simple classification tasks, and reserve paid frontier APIs only for the cases that genuinely need flagship reasoning. One detailed comparison lays out the split plainly: route simple classification/extraction to a self-hosted small model at near-zero marginal cost, and only escalate the minority of complex cases to a paid API.

More specifically for *this* use case — mapping "where do I set up autopay" to a screen — academic work on small on-device models for exactly this kind of intent-to-action mapping found something worth taking seriously: **the most reliable on-device feature is one where the model does the least.** In a real production case study, an ambitious design (LLM generates a full structured output) was abandoned in favor of a much more constrained one (LLM does one narrow task, with a deterministic fallback if it fails) — because the narrow version was dramatically more reliable in practice.

**Recommendation:** Guide needs a **small classification model, not a frontier LLM** — its only job is "map this utterance to one of N known intents, then either deep-link directly or pass a clarifying question back." Keeping this self-hosted by default, rather than aspirational, is the right posture from the start.

### Q2. Where does this classification actually run — on the user's device, or on GoodScore's servers?

**Your pushback here mattered — the first pass at this answer was wrong, and it's worth showing why.**

The first version of this answer leaned on-device: cited research that on-device small models are increasingly viable in 2026, eliminate network round-trips, and keep navigation requests off the network entirely for privacy. You pushed back directly: *these are blue-collar users earning ₹25-40k/month, often single earners or supporting large families, who mostly carry secondhand or Chinese budget phones like Xiaomi — these devices would most likely fail to run an edge language model.*

You were right, and the research backs it up cleanly. **The mistake was treating "on-device SLMs are viable in 2026" as if it applies uniformly to any Android phone.** It doesn't — it applies to the device class the AI/mobile industry actually benchmarks against (flagship and upper-mid-range phones, 8GB+ RAM), not the device class GoodScore's users are actually on.

**What GoodScore's actual users carry:** per the founder's own description, the ICP earns roughly ₹35,000–40,000/month, is often a single earner supporting a larger household, and has already been through a financial shock severe enough to default on multiple loans. The realistic device class is **secondhand handsets or the cheapest current Xiaomi/Redmi-tier models** — researched current pricing shows the high-volume entry segment in India sits at 2–4GB RAM (e.g., Redmi A-series and similar entry models, often under ₹10,000, with some legacy/secondhand devices at 1–2GB still in active use), running a heavier custom Android skin (MIUI/HyperOS) on top, which itself consumes a meaningful share of available RAM before any app even opens.

**Why that rules out on-device inference as the default path:** researched RAM requirements for on-device SLMs are consistent across sources — even the smallest practically useful quantized models (1B parameter class) need a realistic minimum of **~4GB of RAM available**, and that's before accounting for the OS, the GoodScore app itself, and whatever else is running. On a 2–4GB device with MIUI already resident, there typically isn't 4GB of *free* RAM to hand to a model at all — the on-device approach doesn't degrade gracefully here, it simply doesn't run.

**Corrected recommendation: server-side classification by default, full stop — no on-device tier in the v1 design.** Keep the model small and self-hosted on GoodScore's own infrastructure (the Q1 reasoning — cheap, fast, near-zero marginal cost — still holds), but the round-trip happens over the network every time, because that's the only path that works reliably across the actual device fleet. The latency cost of a network round-trip (hundreds of milliseconds on a reasonable connection) is a far smaller risk to the user experience than building a feature that silently fails to run at all on the cheap-and-secondhand devices that make up a large share of GoodScore's actual install base.

**Where on-device could legitimately revisit later:** if GoodScore's telemetry shows a meaningful share of MAU on 6GB+ devices, a *purely additive* on-device fast-path could be considered for that subset only — never as the default, and never something the v1 architecture should assume.

### Q3. How does Guide actually "navigate" the app once it knows the intent — is this custom-built, or does it reuse standard mobile infrastructure?

**Research finding:** this is a solved, standard mobile engineering problem — **deep linking**, and specifically Android App Links / iOS Universal Links, which let any part of an app (or an external trigger) jump directly to a specific screen with parameters, using a verified, secure link structure rather than ad hoc custom routing.

**Recommendation:** Guide should **not invent a custom navigation protocol.** It should classify intent, then construct a standard deep link (e.g., `goodscore://disputes/active` or the App Links equivalent) and hand that to the existing app router — the same mechanism that already powers notifications and external links into the app. This keeps Guide thin: its only real engineering surface is "intent → deep link string," not "intent → custom screen-rendering logic." It also means Guide's reliability is bounded by GoodScore's existing, already-tested navigation infrastructure, not a new parallel system that could drift out of sync with the real app.

### Q4. What's the actual cost of this role at GoodScore's scale — does it even register against real revenue?

The intuition says this role should be cheap — worth actually confirming that, not just assuming it.

**The case for "basically free":** Guide's classification is self-hosted, small-model, sub-100ms, with no per-token frontier API cost in the common path. Self-hosted small-model classification runs at near-zero marginal cost once a (small) GPU footprint is in place — and that footprint can run alongside infrastructure already required elsewhere in the system rather than needing a fresh provisioning decision of its own.

**Recommendation: Guide should not be costed as a standalone line item.** It should be designed to run on existing self-hosted infrastructure, with the only genuinely new cost being the (cheap, one-time) work of training/fine-tuning the intent classifier on GoodScore's actual navigation vocabulary. The broader pattern worth carrying forward: **shared self-hosted infrastructure, role-specific thin logic on top** — not a separately-provisioned stack for every role.

---

### Q5. What happens when Guide gets it wrong — misroutes, or doesn't recognize the intent at all?

**Research finding:** production case studies on small on-device/classification models are blunt about this — **latency and failure affect everyone, not a percentage of users**, when the fallback path isn't designed carefully. The fix that actually worked in production wasn't "make the model smarter," it was **reducing what the model is responsible for** and building a deterministic, fast fallback for everything else.

**Recommendation:** a strict two-step failure path, not an open-ended retry loop:
1. **Low-confidence classification** → Guide asks one clarifying question (not a chat spiral) — e.g., "Did you mean your loans or your credit card bills?"
2. **Still unresolved after one clarification** → hand off to either a search/FAQ surface or a visible "talk to support" path — per Journey 4, this is the exact moment GoodScore's founder described preserving for human agents (humans are reserved for the cases automation can't cleanly resolve).

This keeps Guide's failure mode cheap and bounded — never more than one retry before falling back to something deterministic.

## Summary

**The honest takeaway:** Guide is genuinely the simplest of the four roles in this system — but "simple" here specifically means *narrow scope, small model, deterministic fallback* — not "skip the design work." Ruling out on-device inference given GoodScore's actual device fleet was the one real correction in this doc, and it came from pushing back on an assumption that sounded reasonable in the abstract but didn't survive contact with who GoodScore's users actually are.
